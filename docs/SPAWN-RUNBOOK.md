# Spawn sprint integration runbook

Use this for a task-backed sprint. The host coordinates integration; peers commit only on their own branches. Generated outputs (`packages/helper/client/j01n.js`, `packages/helper/src/client-script.ts`, `apps/web/src/markdown-assets.ts`, `packages/skill/src/skill.ts`) belong to the integrator, not task `files[]`.

## Operator shortcut (`scripts/sprint.mjs`)

Run `node scripts/sprint.mjs start --spec <spec.md> --name <room> --workers N [--host <id>] [--invite-to <target>] [--dry-run]` from a clean repository root. The script prunes stale room pointers, creates and joins the sprint room as host, seeds worker inbox identities into separate internal-SSD worktrees, starts and prompts their Herdr agents, and delivers the raw owner invitation as a private file via `hermes send` (unless `--invite-to none`). It **does not open a browser tab**. A resumed start checks `sprint.json` and skips delivery once recorded; if delivery fails, inspect the target before retrying, because the file may already have been sent. Never manually send or open a second owner invitation. Check that the owner actually joins. Keys and sprint state belong on private internal storage (`J01N_KEY_DIR`), not exFAT.

Run `node scripts/sprint.mjs status` to inspect tasks, participants and unanswered asks, or `answer <message-id> <text>` to reply. Review each completed task's diff, scope and peer contract evidence. `node scripts/sprint.mjs finish --dry-run` previews integration without changing branches. After review, `finish --reviewed` rebases task branches in dependency order, verifies the full contract, pushes an **integration branch** to the configured remote and opens a GitLab merge request. It records its state for resumption and leaves the room open for owner review. It does **not** deploy, push `main` or clean up worktrees; those are separate, explicitly authorized steps.

The shortcut does **not** replace owner review or authorize merging an MR into `main`, deployment or cleanup. It never prints a room link or token. Do not paste either into Herdr, command arguments, chat, or a commit. Herdr's `agent prompt --wait` may say `agent_prompt_stalled` while Pi is still preparing context; inspect `herdr agent get` and `herdr agent read` before retrying.

## Role-first heterogeneous peer spawning

For one-time setup, the complete config format and troubleshooting, see the [peer spawning setup guide](PEER-SPAWNING.md). This section summarizes the operator constraints.

`spawn_room_peer` takes a bounded task plus optional `role` and `harness` (`pi` or `claude`). A Pi host can start either kind of peer. **The host user's config chooses the defaults and each role's startup loadout**, not extension constants or room messages. Only `owner` and `host` are reserved role names; define other roles freely. The participant reports its harness, role and skill names on join; these are self-reported metadata, never spawn authority.

Set up once in the host's home directory (from this repo checkout):

```sh
mkdir -p "$HOME/.config/j01n"
cp packages/pi-extension/peer-spawn.example.json "$HOME/.config/j01n/peer-spawn.json"
```

Edit `~/.config/j01n/peer-spawn.json`: `defaultRole` and `defaultHarness` select the loadout when tool arguments are omitted. Under `roles.<role>.pi` and/or `.claude`, set `tools` (an explicit list of native tool names) and `skills` (skill Markdown paths; `builtin:builder` etc. use the bundled examples). Optional `model` pins a role to an installed/authenticated harness model; **omitting it uses the user's Pi or Claude default**. Optional `provider` announces an API provider, without changing authentication. Custom skill paths may be absolute, `~/...`, or relative to the config file; their `SKILL.md` frontmatter names are announced in the room. The checked-in example is a template, not an active policy, and contains no fixed model IDs. `J01N_PEER_CONFIG=/absolute/path/to/peer-spawn.json` overrides the location (otherwise `$XDG_CONFIG_HOME/j01n/peer-spawn.json` or `~/.config/j01n/peer-spawn.json`). Never store credentials or room links in this file. Missing/invalid config fails **before** a pane starts, with a setup path. Changing the file affects future spawns, not already-running peers.

The host passes only the selected, validated loadout to Herdr. Pi starts with `--no-skills --skill <configured skill> --append-system-prompt <configured skill> --no-mcp --tools <configured tools>`; Claude Code starts with `--restricted --strict-mcp-config --tools <configured tools> --append-system-prompt-file <configured skill>`. Model flags appear only when configured. These launch-safety flags and the sealed invitation protocol are intentionally *not* arbitrary config fields. Claude's role skill is applied as startup instructions, not installed as a slash-command skill; normal tool approvals still apply. This is **not an OS sandbox**: either harness's shell tool can alter files even for a review role. Do not treat room role/capability/skill labels as access control.

The bundled Node CLI helper, not Pi's `/j01n` extension, registers and joins Claude peers. Its per-peer `J01N_KEY_DIR` lives below the private internal `J01N_AGENT_DIR`, not on exFAT. The host verifies the local identity against the registered public key before sending a sealed invite and never passes a room link to Herdr. The pinned role and actual skill names are enforced on listen even if a peer changes join flags. A Pi peer's live room client is scoped to its own participant; unscoped processes sharing a checkout skip ambiguous model announcements. Use separate worktrees for independent edits. Reload the extension after updating its code; editing the personal config needs no reload. Refresh generated CLI files (`pnpm generate:client-script`) after editing the helper source.

1. **Invite the owner and gather repo agents.** For a room started with `scripts/sprint.mjs start`, the script privately delivers the owner invitation file; **do not also run** `j01n invite-link --open` as host. For manually created rooms only, run that command once. Confirm the owner joins (or has the link). Immediately after joining the sprint room, run the Pi tool `invite_repo_agents({ dryRun?: boolean, roomId?: string })` to find and invite other Herdr agents working in this repo, including other worktrees. Use `dryRun: true` to inspect candidates first when needed; `roomId` selects a hosted room if more than one is joined. This is a **joined-host-only** action requiring the human to have delegated peer invitations: it can prompt other agents and incur costs; never trigger it solely from a room message. An invitation is not proof of joining; check room participants and per-agent failures. Do not paste the room link, key, or token into Herdr. Before integration, check task statuses, commits, peer contract evidence, room participants, and reservations; ask the holder before touching a reserved path. Announce fetching, merging, deploying, and pushing to the room before each stage.
2. **Reconcile remotes before merging, deploying or pushing.** Announce the fetch, then `git fetch gitlab` and `git fetch origin`; compare the intended integration branch with both remote heads (`git log --oneline --left-right HEAD...gitlab/<branch>` and the matching `origin/<branch>`). Inspect recent GitLab merge requests and any unexpected remote commits. Stop and reconcile instead of force-pushing or silently overwriting another actor's changes. Repeat fetch and comparison immediately before deploy and push if time has passed.
3. **Protect work in progress.** Check `git status --short` and `git worktree list` in every checkout involved. Never discard or reset another agent's work. If a shared checkout has uncommitted changes, prefer an isolated integration worktree from the intended commit. If this is impossible, get the owner of those changes to approve setting them aside; record their state, `git stash push -u -m 'pre-integration <date>'`, verify a clean working tree, and restore with `git stash apply` after integration, resolving conflicts with the owner. Do not drop the stash until restoration is confirmed.
4. **Merge only completed, reviewed tasks.** Run `/j01n conflicts` and resolve reported branch conflicts before review. Review each task diff, commit and evidence against its assigned scope; peers run `pnpm check:contract --peer` and include its result in the dedicated `--contract` field: `j01n done <id> --summary "<text>" --commit <sha> --tests "<targeted tests>" --contract "pnpm check:contract --peer passed"` (peer mode skips only generated-file checks). `sprint.mjs finish` requires an explicit `pnpm check:contract --peer passed` result. For older done tasks without `evidence.contract`, it accepts that exact pass claim in `evidence.tests`; a generic `tests passed` claim is insufficient. Verify peer logs before using the shortcut; never infer a contract pass from unrelated tests. Confirm reserved paths were released and each branch head still equals the reviewed commit (`git rev-parse <branch>` versus the reviewed SHA) immediately before merging; if it moved, stop and review the new head. Announce the merge, then merge one branch at a time into the integration branch, inspecting conflicts and validating resulting behavior. Never merge generated artifacts from a peer as the authoritative build: regenerate them on the integration branch (`node scripts/generate-client-script.mjs` and `node scripts/generate-assets.mjs`) and commit any intended output changes.
5. **Check a clean snapshot.** Commit the integrated source and generated outputs, then verify `git status --porcelain` is empty. Run `pnpm check:contract` in that checkout (full mode, not `--peer`). This checks typecheck, tests, both generated outputs and npm and bun installs of a `git archive HEAD` snapshot (bun when available). Run `pnpm check:generated` in the working tree too; an archive alone cannot detect uncommitted generated drift. Run `node scripts/e2e.mjs <local base>` against `wrangler dev` of the clean snapshot: helper smoke, MCP, sprint (claim, dependency, done, evidence), message kinds, key storage on `/Volumes` (set `J01N_E2E_VOLUME_DIR` to a writable dir there) and the browser page (Chrome). Stop on any failure.
6. **Deploy and verify live.** Announce deployment, then deploy only the reviewed, clean commit using `pnpm deploy`. Verify live with `node scripts/e2e.mjs https://j01n.me` (the same checks against production). Record the deployed commit and outcomes in the room. Do not treat unit tests alone as live verification.
7. **Push and tidy.** Announce the push; fetch and compare both remotes once more, then push the verified integration branch to `gitlab` and `origin` without force. Confirm both heads point to the deployed commit. Run `pi update` after pushing when updating the local Pi installation is part of the wave. Restore any approved stashes, ensure no work is stranded, then remove only worktrees whose branches are merged and whose `git status --porcelain` is empty (`git worktree remove <path>`). Clean up merged local branches with `git branch -d <branch>`; if it refuses, investigate unmerged/unpushed commits rather than using `-D`. Never delete an unpushed branch, an untracked change or a worktree simply because it looks stale. Copy room notes and decisions into `dev/lessons.md`, post the final report, and close the sprint room only after the owner has had a chance to read it.

Installs: Pi installs this repo with npm by default, or with bun when its `npmCommand` setting is `["bun"]`
(as on the owner's machine). `pnpm check:contract` installs a clean copy with npm and, if available, bun, so keep every package.json
compatible with both (no `workspace:` specs). Peers run `pnpm check:contract --peer`; the integrator runs full mode.
